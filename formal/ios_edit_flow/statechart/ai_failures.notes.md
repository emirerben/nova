# AI failure paths: verdicts (worktree `codex/ios-edit-flow-formal`, base ff27b0a65)

Charts: `ai-turn.mmd` (chat turn), `ai-render.mmd` (making the video), `ai-plan.mmd` (planned videos).
All refs are relative to the repo root; `api/` = `src/apps/api/app/`.

## Background facts (checked, used in the verdicts)

- `Agent.run` ends every failure as a `TerminalError` subclass. A refusal turns into `TerminalError` with `__cause__ = RefusalError` (`api/agents/_runtime.py:574-586`). If every model only gave transient errors, the message is "exhausted N model(s)" (`:676-687`). An explicit spend or billing 429 becomes `ProviderQuotaExceededError`, which is also a `TerminalError` (`api/agents/_provider_errors.py:39-71`, `_runtime.py:128`). A bare 429 is still treated as transient and retried.
- Turn timing: `run_kria_turn` has a 200 s soft limit, a 230 s hard limit and `max_retries=0` (`api/tasks/kria_runtime.py:3052-3058`). The lease lasts 15 s (`api/config.py:883`) and is renewed every 5 s (`kria_runtime.py:158`). `_MAX_ABANDONED_CLAIMS = 3` (`:162`). `reconcile_kria_turns` runs every 60 s (`api/worker.py:322-325`) and waits 1 min before republishing (`kria_runtime.py:156`).
- Main Creator: 3 attempts, 130 s timeout, flash fallback model (`api/agents/main_creator.py:649-676`).
- Approvals expire after 30 min (`api/kria/plan_review.py:949,1297`). The expiry sweep runs inside the reconcile tick (`kria_runtime.py:6750-6760, 6776-6911`).
- Reaper: `THRESHOLD_MIN = 60` (`api/tasks/reaper.py:53`). `sweep_stale_jobs` runs every 5 min (`api/worker.py:259-262`) and skips the whole sweep when Celery `inspect()` returns None (`api/tasks/maintenance.py:500-504`, `reaper.py:356-359, 584-587`). Jobs still in `queued` are never reaped.
- `_STALE_PLAN_GENERATION_AFTER = 10 min` (`api/routes/content_plans.py:50`). It is applied only when someone reads the plan (`:160-196`, called at `:376`).

## Suspected bugs

### A1: spend cap or quota gives a retryable generic failure. Verdict: CONFIRMED (two paths)
Refs: `api/kria/planner.py:2254-2255` (TerminalError rewrapped as RuntimeError), `:5233-5246` (brief on: `_request_recovery("creator_planning_failed")`), `:3841-3870` (copy), `api/routes/_copilot.py:405-411` (copilot TerminalError becomes HTTP 502), `api/tasks/kria_runtime.py:3343-3366` (generic `runtime_turn_failed`, `retryable: True`).
The Gemini monthly spend cap is reached. You ask Kria for an edit and it answers "I couldn't turn that into a plan this time… Try again". With the brief off, or on the copilot path, it says "I couldn't finish that step… Try the request again" instead. You tap retry, the same quota error comes back, and this repeats until someone raises the cap. Nothing in either reply tells you it is a service outage. The class name only reaches `turn.error.error_class` (admin views), and iOS has no code to tell it apart from other failures. `AiBudgetExceededError` (your own budget) ends in the same generic `runtime_turn_failed`.

### A2: any bare ValueError becomes `phone_plan_unsupported` and iOS offers no retry. Verdict: CONFIRMED (wider than reported)
Refs: `api/tasks/generative_build.py:2761-2762` (`isinstance(exc, (UnsupportedPhonePlan, ValueError))`), `api/tasks/kria_runtime.py:4294-4298, 6400` (deterministic, so `recovery: ask_user`), `src/apps/ios/Kria/Features/CreationConfirmationStage.swift:135-139` (`nonRetryablePhoneGateErrorCodes`). Copy: "This edit uses something your iPhone can't render yet. Start a new edit with a different clip or format."
You approve a montage, and something unrelated to the iPhone's abilities raises a `ValueError`. Examples are a pydantic `ValidationError`, `"Phone rendering is unavailable for this account"` (`:4577, 5287, 6552, 8415`), `"No renderable variant for this edit"` or `"Cannot replace a ready phone variant…"`. You are told your iPhone can't render it and there is no Retry button. Another case is the voiceover montage writer: any malformed AI intro text is turned into `UnsupportedPhonePlan("unable to compile intro text")` (`api/pipeline/phone_voiceover_montage_plan.py:309-322`). So a one-off bad answer from the model is reported as a permanent device limit.

### A3: a hard-killed turn re-plans up to 3 times, silently and paid each time. Verdict: CONFIRMED (cause narrowed)
Reviewer note: the count is 3 runs in total (the original plus 2 silent re-plans). The 3rd lapsed lease sets `abandoned_claims=3`, and the next claim fails at `_claim` (`:2637-2638`) without planning. A hard-killed child is requeued at once (`worker.py:152-153`, `task_reject_on_worker_lost`). The redelivered task sees a `planning` row whose lease has not yet lapsed and returns None (`:2626`), so the real re-plan waits for the 15 s lease plus the next 60 s reconcile tick (`:6914-6950`). The reconciler then publishes immediately.
Refs: `api/tasks/kria_runtime.py:6940-6950` (sweep: a lapsed `planning` turn gets `abandoned_claims+1` and goes back to `pending`), `:2626-2642` (a redelivered claim also counts), `:2637-2638, 2884-2911` (the 3rd claim gives `runtime_turn_claims_exhausted`).
The 200 s soft limit does *not* cause this: `SoftTimeLimitExceeded` is caught by `except Exception` and fails the turn visibly (`:3343`). It happens only when the worker process dies, for example from OOM, a deploy SIGKILL or the 230 s hard kill. You send a message and see "Kria is thinking". The worker dies, and about 75 s later the sweep quietly runs the whole plan again, paying for every model call again. If the input reliably crashes the worker, this repeats 3 times (up to 3 × 230 s plus about 3 × 75 s, roughly 15 min). Only then do you see "I couldn't finish that step… Try the request again", and retrying starts the same cycle.

### A4: `OperationalError` re-runs the whole render job up to 7 times, including AI calls. Verdict: CONFIRMED
Refs: `api/tasks/generative_build.py:1989-2005` (`autoretry_for=(OperationalError,)`, `max_retries=7`, `retry_backoff_max=60`), `:2045-2046`, `:2712-2713` (the phone branch re-raises it too), `:2889-2891` (`_NO_RERUN_STATUSES` only skips jobs that already finished).
A short database blip mid-job, after clip analysis and text composition, restarts the job from the top. Landmark naming (`:6394`) and the creation-text composer (`:6461`, 180 s pro then 90 s flash) run and are paid for again before the "already pinned" check at `:6559-6561`. You see "Preparing your clips" for much longer than normal and get no signal that it restarted. The cloud path partly reuses persisted variants and clip-prefetch cache, but intro_writer and the matcher run again.

### A5: a content plan stuck in "generating" has no sweep. Verdict: CHANGED
Refs: `api/routes/content_plans.py:50, 160-196, 376`; `api/tasks/content_plan_build.py:370-375`; `api/routes/creation_threads.py:1664-1667`.
There is still no background sweep. A read-time self-heal now marks the plan `failed` (or `ready` if it already has items) once it has been `generating` for more than 10 min and someone opens it. **iOS never calls `/content-plans`.** iOS videos use a holder plan created with `plan_status="edited"` and no AI, so this path cannot happen from iOS. It does affect web onboarding: you leave during generation, the worker dies, and the database row says "generating" until you open the plan again. One degraded case remains: if "add more ideas" dies on a plan that already has items, the heal marks it `ready` and your new ideas never come, with no message.

### A6: silent degradations. Verdict: CONFIRMED (each one)
- **Brief requirements dropped: CHANGED (reviewer).** `extract_kria_brief` (`api/tasks/kria_runtime.py:3409-3443`) is enqueued only when `planned.defer_brief` is set (`:3247-3255`), and the only producer is `_editor_target_recovery` (`api/kria/planner.py:4138-4157`, callers `:4926, 5381`; `:5077` forces it off). So no edit has been applied in that case. You ask for a change while your video is still rendering (or the editor can't be opened). Kria says "Your edit is still rendering, give it a moment, then ask again", and if the background save then fails your words are never added to the brief. The impact is small, because you were told to ask again anyway. The extract-failure fast path (`_serve_unextracted_edit`, `:3902-3975`) does *not* lose the request: it stores your whole message as one requirement.
- **Excludes fail open**: `api/services/clip_intent_resolution.py:1264-1282`. You say "leave out the quad bike clip", the resolver is down, and the draft keeps every clip with no warning.
- **Generic intro hook**: `api/tasks/generative_build.py:21630-21647`. A refusal gives `_fallback_intro_text` (a generic hook). Any other agent failure returns `(None, {})`, so the video has **no intro text at all**. You are told neither.
- **Whisper transcript**: `api/pipeline/agents/gemini_analyzer.py:1040-1052`. Gemini fails, Whisper is used, and if Whisper also fails you get an empty transcript with `low_confidence`. Quota is the one error that passes through here.
- **Best-moment fallback**: `api/tasks/template_orchestrate.py:2706-2712` (`_fallback_moments`, `moments_synthetic`) and `:2726-2760`. A clip that fails analysis is rebuilt from Whisper words with evenly spread moments (`analysis_degraded=True`). That `except (… Exception)` also catches `ProviderQuotaExceededError`, so during a spend-cap outage every cloud render quietly turns into a heuristic edit.

## Items the exploration left unverified

- **Edit copilot timeout and schema handling**: 2 attempts, 120 s spec timeout (`api/agents/edit_copilot.py:3290-3299`). The route override is 40 s (`api/routes/_copilot.py:364`). Kria's main editor call uses 120 s plus the turn deadline (`api/kria/planner.py:1950-1964`). Reviewer: the scoped "Review your video" update inside Kria calls it with no override, so it gets the 40 s default and no deadline (`api/kria/planner.py:4722-4730`). A TerminalError (schema, refusal, quota, transient exhausted) becomes HTTP 502 `edit_copilot_failed`. Inside a Kria turn nothing catches that exception except `_serve_unextracted_edit`, so the turn ends `runtime_turn_failed`. A timeout gives `ProviderOutcomeUnknownError`, which becomes `runtime_provider_outcome_unknown` ("I couldn't get a completed response from the AI service…"). When the model returns ops together with a non-edit intent, the ops are dropped and `_honest_outcome` writes the honest reply (`_copilot.py:449-456`).
- **Speech cleanup failure**: preflight failure codes and whether each is retryable are listed at `api/services/speech_cleanup_preflight.py:44-53`. A transcription failure becomes `transcription_unavailable`, which is retryable (`api/tasks/speech_cleanup_analysis.py:609-620`). If cleanup was required at render time, `SpeechCleanupFailure` gives `failure_reason="speech_cleanup_failed"` (`api/tasks/generative_build.py:2093-2109`) with the copy "Cleaning up the audio didn't finish. Try again, or turn off speech cleanup." On the confirmation card, iOS offers "Create without cleanup".
- **Voiceover montage writer**: see A2. A hook-writer failure is degraded (generic hook or none, `generative_build.py:5041-5050`). Bad AI intro content is reported as `phone_plan_unsupported` with no retry. A creator-confirmed opening title skips intro_writer entirely (`:5031-5039`).
- **Thresholds**: `_STALE_PLAN_GENERATION_AFTER` = 10 min. Reaper `THRESHOLD_MIN` = 60 min, on a 5-min sweep.
- **iOS mapping of `runtime_turn_claims_exhausted`**: there is no special mapping. It is not in `nonRetryablePhoneGateErrorCodes`, so it is treated as retryable, and the server's `content` copy is shown ("I couldn't finish that step, but your project and saved draft are safe. Try the request again."). This is harmless on its own but hides A3.

## Reviewer corrections to the charts

- `ai-turn`: removed the invented edge from "single text edit without reading the request" to "request not saved". The deferred brief save follows the "still rendering, ask again" reply instead. Added the brief-off Main Creator failure (an uncaught `RuntimeError` becomes `runtime_turn_failed`, `planner.py:5243-5248`). The dispatch outcome-unknown state now shows a way forward (send a new message).
- `ai-render`: replaced "worker killed, frozen until the reaper" with the real redelivery loop (N6). The reaper and the skipped sweep now hang off "task lost". The speech-cleanup failure moved from the cloud transcribe step to the routing step (it is raised in `talking_head_assembler.py` and re-raised by the phone branch, `generative_build.py:2723-2727`). The music step was relabelled as an auto-pick (N4 refuted).
- `ai-plan`: `generate_content_plan` *does* retry automatically. `_fail` marks the plan `failed` and then calls `self.retry` (`max_retries=2`, 10 s apart, `content_plan_build.py:200-205, 290-304`), so the plan shows "failed" between tries and can then flip to "ready". The old "no auto-retry" label was wrong.

## NEW paths found

- **N1: render dispatch "outcome unknown" is never reconciled. NEW, downgraded by the reviewer from stuck to failed with a misleading promise.** It applies only to a re-render of an existing video (the editor-commit branch, `:5440-5471`; the device branch is a no-op that cannot throw, and first renders go through `dispatch_item_render_for`). The session goes back to `awaiting_feedback`, so you can still send a new message and get a new draft. iOS shows "Refresh project", not "Retry approved edit" (`ChatWorkspaceView.swift:1810`), and the manual retry route refuses `outcome_unknown` anyway (`api/kria/render_retry.py:161-165`). The original finding follows. `api/tasks/kria_runtime.py:5308-5350, 5464-5471`. If publishing an editor render throws, the execution is set to `outcome_unknown` (`recovery: manual`, `retryable: False`) and the turn fails with "I won't send it twice until it is reconciled". No sweep ever picks up `outcome_unknown` executions; the reconciler only looks at `accepted` and `dispatched` (`:6952, 6981`). iOS shows no Retry for it, because `failedRenderExecutionID` needs `recovery == "retry"`. If the render actually ran, the thread never learns about it.
- **N2, degraded: a spend cap during cloud clip analysis is invisible.** See the last A6 bullet. Quota is caught as a generic analysis failure, so the edit renders from Whisper guesses.
- **N3, degraded copy: `processing_timeout` always blames "heavy 4K/HDR clips"** (`api/tasks/generative_build.py:2130-2160`), even when the 29 minutes went to slow AI calls or to A4 restarts.
- **N4: the music matcher silently drops a requested song. REFUTED by the reviewer.** `_match_best_track` (`api/tasks/generative_build.py:21751-21800`) has only two callers, and both are auto-picks when you chose no song: the voiceover montage writer (`:5062`), and the guided plan when no song was frozen at approval (`:10688-10701`, skipped when `frozen_status`, narration or `user_song` is set). A song you picked at approval is frozen as `selected` and either used or rejected loudly (`approved_licensed_music_stale`, `:10705-10713`). The v2 smart music bed returns only a treatment you chose yourself while `SMART_MUSIC_BED_REQUIRES_REQUEST_ENABLED` is true, which is the default (`:27472-27483`). A matcher failure therefore means "no auto song added", which is a mild degradation and not a dropped request.
- **N5: the frozen-job sweep can skip forever. NEW, narrowed by the reviewer.** If Celery `inspect()` keeps timing out (a busy broker), `sweep_stale_jobs` returns 0 on every tick (`api/tasks/maintenance.py:500-504`, `reaper.py:356-359, 584-587`). This matters only when the task message is lost. A killed worker normally causes a redelivery: `task_acks_late` plus `task_reject_on_worker_lost` (`api/worker.py:152-153`) requeue a killed child immediately, and a lost machine's message comes back after `visibility_timeout=1900` s (`:185`), which is before the 60-min reaper threshold.
- **N6 (reviewer), stuck: a killed render reruns the whole job with no cap.** Refs: `api/worker.py:152-153, 185`; `api/tasks/generative_build.py:2889-2891` (`processing` is not in `_NO_RERUN_STATUSES`); `api/tasks/generative_build.py:6333-6337` (the phone montage skips only when the device already rendered this generation, so a pinned `guided_edit` does not stop the landmark and text-composer calls). Nothing counts redeliveries. You approve a heavy edit and the worker runs out of memory. The task is requeued and starts again from the top, paying for the AI calls again. If the same footage runs out of memory every time, this repeats indefinitely, because the reaper never fires while the task is live in Celery. The status route sets a `retrying` flag from `job_heartbeat` (`api/services/job_phases.py:381-396`), but iOS never reads it, so you just see the video still in progress.
- **N7 (reviewer), stuck copy: the phone kill switch is reported as a device limit.** `_run_phone_unified_montage_job` raises a bare `ValueError("Phone rendering is currently unavailable; originals remain on the device.")` when phone rendering is turned off globally (`api/tasks/generative_build.py:6337-6340`). The same happens for the per-account check (`:6551-6552`). Both become `phone_plan_unsupported`. During a temporary ops kill switch you are told "This edit uses something your iPhone can't render yet. Start a new edit" with no Retry, even though the same edit works once the switch is back on. A `PhoneCapabilityUnavailable` (retryable) code already exists for exactly this case (`:2733-2753`). This sharpens A2.
- Slides: the composer fails open to your asset order, but the server copy is honest ("Kria could not complete a composition, so this keeps the selected asset order.", `api/routes/plan_items.py:5098-5106`). iOS shows `summary`, though it ignores `fallback_used`. **Not a bug.**
- `edit_proposal` is reached only through web `plan-items` routes (`api/routes/plan_items.py:3380, 3922, 4072`), not the iOS v2 runtime. Listed in the table only.
