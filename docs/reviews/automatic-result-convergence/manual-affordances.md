# Remaining actions in the touched routes

This is a source-review inventory, not executed UI evidence. The current working tree is not yet frozen/rebased. Labels below distinguish a real user decision from a reload disguised as repair.

| Affordance | Classification and behavior |
| --- | --- |
| Generic chat failure “Refresh project” | Removed. It only reloaded project/delta state and could not repair a terminal render. The existing live poll continues; fallback copy directs a new chat instruction. |
| Approved-render retry with no execution ID | No dispatch and no instruction to refresh manually. The authoritative projection may already have moved on; the existing chat live poll follows it. A specific failed execution is required before a real retry. |
| “Retry approved edit” | Explicit action against an exact failed execution and thread revision. It is not automatically repeated after an uncertain outcome. |
| “Retry message” in general chat | Existing original-submission reconciliation; the copy says it checks the same submission. It is distinct from a new user message. |
| “Retry preparing clips” / failed upload retry | Explicit failed preparation/upload action when the server marks it retryable. Processing/status reads converge automatically; no blind repeat of an uncertain upload is introduced. |
| Native editor conflict choices | Removed. The editor converges onto the latest version, keeps the creator's non-overlapping edits, and the latest version wins an overlap. Replaced edits go to Undo. Save, play and export are never blocked. |
| SlidePost conflict choices | Still a user choice for genuine overlapping authored changes or connected timing/source dependencies. Independent changes merge automatically. Tracked as KRI-1369. |
| Native “Switch / Keep editing” | Still exists (the “Switching discards your unsaved edits” prompt), tracked as KRI-1368. It appears only when a matching authoritative editable base is unavailable for a dirty different-job target. Clean/newer results and mergeable dirty content follow automatically. Switch explicitly discards the old local version; it is not a routine refresh path. |
| Native unsafe song choice | Removed. When the song authority changed, the editor shows the latest song and does not reapply old relative song edits to it. The creator can edit the new song. Saved-song metadata/acknowledgement handles the legitimate old-render-plan projection case. |
| Strict AI “Check original result” | Pure GET observation of the original UUID; it cannot POST, publish or call a provider. Automatic paced observation continues beyond fast-budget exhaustion. Newly accepted pending work is delivered by the durable server outbox, not a required click. A separate first-admission continuation is allowed only when the journal atomically proves no prior attempt. |
| Strict AI new instruction after rejection/unknown | A new explicit user intent, not automatic Retry of paid work. Authoritative rejection permits explicit new Send, including the same text; unknown/running results remain observation-only. Legacy pending requests without execution evidence remain unresolved and observed without reconstruction, rejection or an invitation to paid resend. No new UUID/provider execution is minted by recovery GET. |
| Render Create after confirmed terminal failure | New explicit render intent only after a fresh exact-job failure receipt/state. New admission also compares current Job and draft version under lock. Pending/unknown work is observed automatically using its original identity. |
| Export “Try again” after render/poll budget | Starts a bounded new export/check flow; it must observe existing render intent rather than issue duplicate generation. Photos/share transaction evidence is a separate gate. |
| Retry/remove failed media | A genuine source preparation failure. Invalid/unavailable input cannot be made ready by reloading; the user may retry the failed preparation or replace/remove that input. |
| Workspace/editor opening “Try again” | Client read-budget exhaustion or an explicit unsupported/missing prerequisite; automatic quiet retries run first. This action does not imply the underlying generation failed. |
| Review read-budget exhaustion | Candidate replaces the reopen instruction with a slow read-only follower after six failures or the fast-follow time window. Cursor/project changes and foreground also trigger paced reads. One reader, current thread/account/environment and dismissal checks fence adoption. Native regression execution remains pending. |
| Gallery/device read-budget exhaustion | Candidate retains one coalesced five-minute status read after twelve fast retries. Stop, shutdown, settlement and account replacement cancel or fence recovery. Server pacing survives competing reads; explicit Resume retains only its original target authorization. Native regression execution remains pending. |

SlidePost conflict, unavailable identity/base, unsupported input, device permission and terminal execution failure remain explicit boundaries. Other exhausted read budgets listed above require separate classification; this inventory does not establish automatic convergence for every outage duration. Neither a client read budget nor a recovery affordance proves that background work restarted, failed or delivered. Candidate source behavior still needs final-source native and integration evidence.
