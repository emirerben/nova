# Recover a completed iPhone video after an app update

## Incident and acceptance

The creator reported that the latest lip-sync video worked before a Kria app update.
After reopening, the chat alternated between "Your plan is ready" and the local
ready card. Playback and the editor were inaccessible.

Acceptance is to reopen the same completed video after app-container relocation,
keep playback and editor access during sync, and publish the correct bytes.
An unchanged export must not encode again. Regenerated bytes must not reuse an
upload reservation for different bytes. A newer recipe must still render, and an
export that requires verification must not expose playback before it passes.

This is a follow-up to the phone-render lifecycle work in KRI-934. It does not
close that incident or claim that the installed TestFlight app has been repaired.

## Observed production evidence

Read-only diagnostics on 28 October 2026 found a lip-sync job at recipe revision 2
with server phase `syncing`. Its reserved object did not exist in storage.
The paired iPhone held both its original completed export and a later completed
export. Their checkpoints named different application containers. The current
local receipt's byte count and SHA-256 differed from the server reservation for
the same attempt. Raw records and media remain outside Git.

The coordinator persisted an absolute export URL. A relocated app container made
that URL unusable. Recovery encoded again with the same attempt identifier.
Upload reservation rejects different bytes under that identifier. Reconciliation
retried the conflict. The chat's plan feed also accepted finished build phases
when no error message existed, and its editor switch required server readiness.

## Data ownership and design

`DeviceRenderReceipt` binds a recipe request, an upload attempt, an output URL,
and a byte fingerprint. The coordinator owns their lifecycle. A request identifies
the edit. An attempt identifies immutable exported bytes.

On reopen, resolve the attempt's MP4 inside the current render directory and
accept it only when its fingerprint matches. Reuse the attempt and bytes.
If the output is missing or changed, create a new attempt before an encode.
If an older build already reused an attempt, the publisher maps the specific
reservation refusal to a typed error. The coordinator copies the verified local
export to a fresh attempt and retries publication without encoding.

The chat gives finished exports to the device status card. A local verified file
keeps the editor switch available while publication is pending. Output verification
continues to withhold access when required.

## Failure modes and checks

The regression tests were written before the corresponding fixes.

| Case | Expected observation |
| --- | --- |
| Relocated local-ready export | Current path, same attempt, one encode total, successful publication |
| Relocated synced export | Current path, same attempt, no new encode |
| Missing output | New attempt before regeneration |
| Corrupted output | Reject the changed bytes and regenerate under a new attempt |
| Existing reservation collision | Fresh attempt, same export, one encode total |
| Repeated sync conflict | Stable playback and an accessible editor |
| Initial phone build | Progressive plan feed until the export exists |
| Transient read, capability, or recovery failures | Existing recovery checks continue to pass |

The corrupted-output case is the negative control for byte identity. Equal file
names or a completed receipt alone must not admit altered output.
